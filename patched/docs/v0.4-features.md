## 1. Extension Hooks — Система расширений

### Обзор

Extension Hooks — точки врезки в жизненный цикл операций (retain, recall, reflect,
consolidate, mental models). Реализованы по паттерну Interceptor / Middleware.
Pre-hooks — блокирующие (могут запретить операцию), post-hooks — неблокирующие
(ошибки логируются, но не влияют на результат).

### Архитектура

```
┌──────────────┐     ┌───────────────────┐     ┌──────────────────┐
│  HTTP Request │────▶│ validate_retain() │────▶│  Retain Pipeline │
│               │     │ validate_recall() │     │                  │
│               │     │ validate_reflect()│     │                  │
└──────────────┘     └───────────────────┘     └────────┬─────────┘
                      Pre-hooks (blocking)               │
                                                         ▼
                                                ┌──────────────────┐
                                                │on_retain_complete │
                                                │on_recall_complete │
                                                │on_reflect_complete│
                                                └──────────────────┘
                                                Post-hooks (non-blocking)
```

### Ключевые файлы

| Файл | Назначение |
|------|-----------|
| `hindsight-api/hindsight_api/extensions/operation_validator.py` | Абстрактный класс с 10+ hook-методами (534 строки) |
| `hindsight-api/hindsight_api/extensions/base.py` | Базовый класс Extension |

### Подключение

Расширение загружается динамически из переменной окружения:

```bash
HINDSIGHT_API_OPERATION_VALIDATOR_EXTENSION=mypackage.validators:MyValidator
HINDSIGHT_API_OPERATION_VALIDATOR_MAX_REQUESTS=100  # Передаётся в config
```

### Доступные хуки

**Pre-operation (блокирующие) — возвращают `ValidationResult`:**

- `validate_retain(RetainContext)` — перед сохранением памяти
- `validate_recall(RecallContext)` — перед извлечением памяти
- `validate_reflect(ReflectContext)` — перед рассуждением
- `validate_consolidate(ConsolidateContext)` — перед консолидацией
- `validate_mental_model_get(MentalModelGetContext)` — перед чтением ментальной модели
- `validate_mental_model_refresh(MentalModelRefreshContext)` — перед обновлением модели

**Post-operation (неблокирующие) — void:**

- `on_retain_complete(RetainResult)`
- `on_recall_complete(RecallResult)`
- `on_reflect_complete(ReflectResultContext)`
- `on_consolidate_complete(ConsolidateResult)`
- `on_mental_model_get_complete(MentalModelGetResult)`
- `on_mental_model_refresh_complete(MentalModelRefreshResult)`

### ValidationResult

```python
@dataclass
class ValidationResult:
    allowed: bool
    reason: str | None = None
    status_code: int = 403  # HTTP код при отказе

    @classmethod
    def accept(cls) -> "ValidationResult": ...

    @classmethod
    def reject(cls, reason: str, status_code: int = 403) -> "ValidationResult": ...
```

### Контексты операций

Каждый pre-hook получает dataclass со всеми параметрами запроса:

- **RetainContext**: `bank_id`, `contents`, `request_context`, `document_id`, `fact_type_override`, `confidence_score`
- **RecallContext**: `bank_id`, `query`, `request_context`, `budget`, `max_tokens`, `enable_trace`, `fact_types`, `question_date`, `include_entities`, `max_entity_tokens`, `include_chunks`, `max_chunk_tokens`
- **ReflectContext**: `bank_id`, `query`, `request_context`, `budget`, `context`
- **MentalModelGetContext**: `bank_id`, `mental_model_id`, `request_context`
- **MentalModelRefreshContext**: `bank_id`, `mental_model_id` (None для create), `request_context`
- **ConsolidateContext**: `bank_id`, `request_context`

Post-hook результаты добавляют к контексту: `success`, `error`, и operation-specific данные
(например, `unit_ids` для retain, `token counts` для mental model refresh).

### Пример: Rate Limiter

```python
class RateLimitingValidator(OperationValidatorExtension):
    def __init__(self, config: dict):
        super().__init__(config)
        self.max_attempts = int(config.get("max_attempts", "2"))
        self.retain_counts: dict[str, int] = defaultdict(int)

    async def validate_retain(self, ctx: RetainContext) -> ValidationResult:
        self.retain_counts[ctx.bank_id] += 1
        if self.retain_counts[ctx.bank_id] > self.max_attempts:
            return ValidationResult.reject(
                f"Retain limit exceeded for bank {ctx.bank_id}"
            )
        return ValidationResult.accept()

    async def validate_recall(self, ctx: RecallContext) -> ValidationResult:
        return ValidationResult.accept()

    async def validate_reflect(self, ctx: ReflectContext) -> ValidationResult:
        return ValidationResult.accept()
```

### Типичные use-cases

- **Rate limiting / квоты** (pre-hook)
- **Проверка прав доступа / контент-фильтрация** (pre-hook)
- **Audit logging** (post-hook)
- **Usage tracking / billing** (post-hook)
- **Custom metrics** (post-hook)

### Порядок выполнения

1. Pre-operation validation (`validate_*`) — до операции; может отклонить через `ValidationResult.reject()`
2. Операция выполняется, если валидация прошла
3. Post-operation hook (`on_*_complete`) — после операции; исключения логируются, но не влияют на результат

## 2. CLI флаги `--wait` и `--date`

### `--wait` для `bank consolidate`

**Команда:**

```bash
hindsight bank consolidate <bank_id> --wait [--poll-interval 10]
```

**Определение в Rust** (`hindsight-cli/src/main.rs:259-271`):

```rust
Consolidate {
    bank_id: String,
    #[arg(long)]
    wait: bool,                          // Ожидать завершения
    #[arg(long, default_value = "10")]
    poll_interval: u64,                  // Интервал опроса (сек)
}
```

**Алгоритм работы** (`hindsight-cli/src/commands/bank.rs:499-602`):

1. `POST /v1/default/banks/{bank_id}/consolidate` → получает `operation_id` + `deduplicated: bool`
2. Если `--wait` указан:
   - Цикл: `sleep(poll_interval)` → `GET .../operations` → найти операцию по ID
   - `status == "completed"` → выход (успех)
   - `status == "failed"` → выход (код 1, сообщение об ошибке)
   - Иной статус → продолжать, показать elapsed time
3. Без `--wait`: вывести `operation_id`, предложить `hindsight operation get`

**API endpoint:** `POST /v1/default/banks/{bank_id}/consolidate` → `ConsolidationResponse`:

```python
operation_id: str
deduplicated: bool = Field(default=False, description="True if existing pending task reused")
```

**Команда:**

```bash
hindsight document list <bank_id> --date yesterday   # по умолчанию
hindsight document list <bank_id> --date today
hindsight document list <bank_id> --date all
hindsight document list <bank_id> --date 2026-01-15  # конкретная дата
```

**Определение в Rust** (`hindsight-cli/src/main.rs:441-462`):

```rust
List {
    bank_id: String,
    #[arg(short = 'q', long)]
    query: Option<String>,
    #[arg(short = 'd', long)]
    date: Option<String>,              // yesterday | today | all | YYYY-MM-DD
    #[arg(short = 'l', long, default_value = "100")]
    limit: i32,
    #[arg(short = 's', long, default_value = "0")]
    offset: i32,
}
```

**Алгоритм** (`hindsight-cli/src/commands/document.rs:62-141`):

1. Загрузить все документы пакетами по 500: `GET .../documents?limit=500&offset=...`
2. Для каждого документа: распарсить `created_at` → извлечь дату
3. Отфильтровать по целевой дате
4. Группировка в `BTreeMap` (новейшие первые)
5. Вывод: по группам дат с заголовками (или JSON/YAML для машинного формата)

**Примечание:** Фильтрация — клиент-сайд. API не имеет серверного параметра фильтрации по дате.
CLI скачивает все документы и фильтрует локально.

## 3. Agentic Reflect — Агентное рассуждение

### Обзор

Reflect — disposition-aware система рассуждений, реализованная как полноценный агентный
цикл с native tool calling. LLM автономно решает, какие источники запросить и в каком порядке,
используя иерархическую стратегию поиска: mental models → observations → raw facts.

### Ключевые файлы

| Файл | Назначение |
|------|-----------|
| `hindsight-api/hindsight_api/api/http.py:1872-1989` | HTTP endpoint |
| `hindsight-api/hindsight_api/engine/reflect/agent.py` | Агентный цикл (ядро) |
| `hindsight-api/hindsight_api/engine/reflect/models.py` | Pydantic-модели |
| `hindsight-api/hindsight_api/engine/reflect/prompts.py` | Системные промпты и директивы |
| `hindsight-api/hindsight_api/engine/reflect/tools.py` | Реализация инструментов |
| `hindsight-api/hindsight_api/engine/reflect/tools_schema.py` | JSON-схемы инструментов |
| `hindsight-api/hindsight_api/engine/memory_engine.py:3539+` | Точка входа `reflect_async` |
| `hindsight-docs/docs/developer/reflect.mdx` | Архитектурное руководство |
| `hindsight-docs/docs/developer/api/reflect.mdx` | API-справка |

### End-to-End Flow

```
HTTP Request (POST /v1/default/banks/{bank_id}/reflect)
    │
    ▼
reflect_async()
    │
    ├── 1. Аутентификация + валидация (Extension Hook: validate_reflect)
    ├── 2. Загрузка профиля банка (name, disposition, mission)
    ├── 3. Загрузка директив (hard rules из dedicated table)
    ├── 4. Проверка наличия mental models
    ├── 5. Создание tool callbacks:
    │       • search_mental_models()    ← Уровень 1 (приоритет)
    │       • search_observations()     ← Уровень 2
    │       • recall()                  ← Уровень 3 (ground truth)
    │       • expand()                  ← Контекст документа
    │
    ▼
run_reflect_agent()
    │
    LOOP (до max_iterations, зависит от budget):
    │   ├── Вызов LLM с native tool calling
    │   ├── LLM выбирает инструмент и параметры
    │   ├── Выполнение инструмента → результат добавляется в историю
    │   ├── Валидация ID (предотвращение галлюцинированных цитат)
    │   └── done() вызван? → выход из цикла
    │
    ▼
ReflectResponse (text + based_on + trace + structured_output)
```

### Dispositions — «Характер» банка памяти

Три черты по шкале 1–5, инъектируются в системный промпт и влияют на интерпретацию:

| Черта | Низкая (1) | Высокая (5) | Влияние |
|-------|-----------|-------------|---------|
| **Skepticism** | Доверчивый, принимает информацию | Скептичный, ставит под сомнение | Как агент взвешивает доказательства |
| **Literalism** | Гибкий, читает между строк | Буквальный, берёт как есть | Степень inference vs. точное следование фактам |
| **Empathy** | Отстранённый, фактический | Эмпатичный, учитывает эмоции | Учёт эмоционального контекста |

**Пример — одни и те же факты, разные выводы:**

Банк A (low skepticism, high empathy):
> «Удалённая работа улучшает work-life balance. Команда счастливее и продуктивнее...»

Банк B (high skepticism, low empathy):
> «Заявления о пользе удалёнки требуют проверки. Каковы реальные метрики производительности?»

### Directives — жёсткие правила

В отличие от dispositions (мягкое влияние), directives — обязательные ограничения:

| Аспект | Disposition | Directive |
|--------|------------|-----------|
| Природа | Мягкое влияние | Жёсткое правило |
| Эффект | Формирует интерпретацию | Должно соблюдаться точно |
| Нарушение | Допустимо | Недопустимо |
| Пример | High skepticism | «Никогда не ставь медицинские диагнозы» |

Директивы инъектируются в начале **и** в конце системного промпта для максимального внимания LLM:

```
## DIRECTIVES (MANDATORY)
These are hard rules you MUST follow in ALL responses:
- [rule 1]
- [rule 2]
NEVER violate these directives.

[... основной промпт ...]

## REMINDER: MANDATORY DIRECTIVES
Before responding, ensure your answer complies with ALL of these directives:
1. [rule 1]
2. [rule 2]
```

### Budget — глубина исследования

```
base_max_iterations = 10

LOW:  0.5x → 5 итераций   — «Быстро, mental models достаточно»
MID:  1.0x → 10 итераций  — «Баланс полноты и скорости»
HIGH: 2.0x → 20 итераций  — «Исследовать всё, expand() для контекста»
```

### 5 инструментов агента

1. **`search_mental_models`** — Поиск кураторских ментальных моделей (наивысший приоритет)
   - Вход: `query`, `max_results`, `reason`
   - Выход: модели с `content`, `relevance`, `is_stale`

2. **`search_observations`** — Поиск автоконсолидированных наблюдений
   - Вход: `query`, `max_tokens`, `reason`
   - Выход: наблюдения с `is_stale` флагом

3. **`recall`** — Поиск сырых фактов (ground truth)
   - Вход: `query`, `max_tokens`, `reason`
   - Выход: индивидуальные факты с timestamps

4. **`expand`** — Получение полного текста чанков/документов
   - Вход: `memory_ids`, `depth` ("chunk" | "document"), `reason`
   - Выход: полный текст контента

5. **`done`** — Завершение с ответом и цитатами
   - Вход: `answer`, `memory_ids`, `mental_model_ids`, `observation_ids`, `reasoning`
   - Валидация: только реально полученные ID могут быть процитированы

### Защита от галлюцинированных цитат

```python
available_memory_ids: set[str] = set()
available_mental_model_ids: set[str] = set()
available_observation_ids: set[str] = set()

# Каждый tool добавляет ID в множества
# done() проверяет: цитируемые ID ∈ available_*_ids
```

### Request/Response модели

**ReflectRequest:**

```python
query: str                              # Вопрос
budget: Budget = LOW                    # "low" | "mid" | "high"
context: str | None = None              # DEPRECATED (объединяется с query)
max_tokens: int = 4096                  # Лимит длины ответа
include: ReflectIncludeOptions = {}     # {"facts": {}, "tool_calls": {"output": true/false}}
response_schema: dict | None = None     # JSON Schema для structured output
tags: list[str] | None = None           # Фильтр по тегам
tags_match: TagsMatch = "any"           # "any" | "all" | "any_strict" | "all_strict"
```

**ReflectResponse:**

```python
text: str                               # Финальный ответ
based_on: ReflectBasedOn | None         # Доказательная база (если include.facts)
    ├── memories: list[ReflectFact]
    ├── mental_models: list[ReflectMentalModel]
    └── directives: list[ReflectDirective]
structured_output: dict | None          # Структурированный вывод (если response_schema)
usage: TokenUsage | None                # Метрики токенов
trace: ReflectTrace | None              # Трейс агента (если include.tool_calls)
    ├── tool_calls: list[ReflectToolCall]
    └── llm_calls: list[ReflectLLMCall]
```

### Structured Output

При передаче `response_schema` (JSON Schema) reflect генерирует структурированный вывод:

```python
# Запрос
response_schema = {
    "type": "object",
    "properties": {
        "summary": {"type": "string"},
        "key_points": {"type": "array", "items": {"type": "string"}},
        "confidence": {"type": "number"}
    },
    "required": ["summary", "key_points"]
}

# Ответ
structured_output = {
    "summary": "...",
    "key_points": ["...", "..."],
    "confidence": 0.95
}
```

Реализация: агент генерирует текстовый ответ, затем второй вызов LLM извлекает
структурированные данные по Pydantic-схеме.

## 4. Custom Extraction Prompts — Кастомные промпты извлечения

### Обзор

Позволяет пользователям предоставлять собственные инструкции для извлечения фактов
из контента при операции retain. Промпт разделён на структурную часть (формат вывода,
coreference resolution, обработка времени, сущности) и guidelines-часть (что именно
извлекать). Custom mode заменяет только guidelines, сохраняя всю структуру.

### Ключевые файлы

| Файл | Назначение |
|------|-----------|
| `hindsight-api/hindsight_api/config.py:120-121, 224-226, 416-418` | Конфигурация |
| `hindsight-api/hindsight_api/engine/retain/fact_extraction.py:435-559, 719-743` | Промпты и логика |
| `hindsight-api/hindsight_api/engine/retain/orchestrator.py` | Оркестратор retain |
| `hindsight-docs/docs/developer/configuration.md:438-482` | Документация |
| `hindsight-api/tests/test_retain.py:2085-2129+` | Тесты |

### Конфигурация

```bash
# Режим извлечения: concise (default), verbose, custom
HINDSIGHT_API_RETAIN_EXTRACTION_MODE=custom

# Кастомные инструкции (обязательны при mode=custom)
HINDSIGHT_API_RETAIN_CUSTOM_INSTRUCTIONS="Your custom guidelines here..."
```

### Структура промпта

```
┌─────────────────────────────────────┐
│  _BASE_FACT_EXTRACTION_PROMPT       │  ← Общая структура (неизменная)
│  ┌───────────────────────────────┐  │
│  │ {extraction_guidelines}       │  │  ← ЗАМЕНЯЕМАЯ ЧАСТЬ
│  │ (concise / verbose / custom)  │  │
│  └───────────────────────────────┘  │
│  Output format, entities, temporal  │  ← Неизменная часть
└─────────────────────────────────────┘
```

### Логика выбора режима

```python
# fact_extraction.py:723-743
config = get_config()
extraction_mode = config.retain_extraction_mode

if extraction_mode == "custom":
    if not config.retain_custom_instructions:
        logger.warning(
            "extraction_mode='custom' but HINDSIGHT_API_RETAIN_CUSTOM_INSTRUCTIONS not set. "
            "Falling back to 'concise' mode."
        )
        base_prompt = CONCISE_FACT_EXTRACTION_PROMPT
    else:
        base_prompt = CUSTOM_FACT_EXTRACTION_PROMPT
        prompt = base_prompt.format(
            fact_types_instruction=fact_types_instruction,
            custom_instructions=config.retain_custom_instructions,
        )
elif extraction_mode == "verbose":
    base_prompt = VERBOSE_FACT_EXTRACTION_PROMPT
else:
    base_prompt = CONCISE_FACT_EXTRACTION_PROMPT
```

### Пример: только технические решения

```bash
export HINDSIGHT_API_RETAIN_EXTRACTION_MODE=custom
export HINDSIGHT_API_RETAIN_CUSTOM_INSTRUCTIONS="ONLY extract facts that are:
✅ Technical decisions and their rationale
✅ Architecture patterns and design choices
✅ Performance metrics and benchmarks
✅ Code reviews and feedback

DO NOT extract:
❌ Generic greetings or pleasantries
❌ Process chatter ('let me check', 'one moment')
❌ Repeated information already captured

CONSOLIDATE related technical discussions into ONE fact when possible.
Ask yourself: 'Would this technical context be useful in 6 months?' If no, skip it."
```

### Пример: фильтр по языку (из тестов)

```bash
export HINDSIGHT_API_RETAIN_EXTRACTION_MODE=custom
export HINDSIGHT_API_RETAIN_CUSTOM_INSTRUCTIONS="ONLY extract facts that are in ITALIAN language.

DO NOT extract:
❌ Facts in English
❌ Facts in any other language besides Italian

If the text contains both Italian and English content, extract ONLY the Italian facts."
```

Результат: из смешанного текста (англ. + итал.) извлекаются только итальянские факты.

### Что сохраняется при custom mode

Независимо от пользовательских инструкций, следующие части промпта остаются неизменными:
- Формат вывода (JSON-структура фактов)
- Coreference resolution (разрешение местоимений)
- Обработка временных меток
- Извлечение сущностей (entities)

## 5. Worker Service — Сервис фоновых задач

### Обзор

Распределённая система фоновой обработки задач. Использует PostgreSQL как брокер
(вместо внешних очередей типа Redis/RabbitMQ). `FOR UPDATE SKIP LOCKED` обеспечивает
безопасное конкурентное извлечение задач без дублирования.

### Архитектура

```
                   ┌─────────────┐
                   │  API Server  │
                   │              │
                   │ submit_task()│
                   └──────┬───────┘
                          │ INSERT INTO async_operations
                          ▼
              ┌───────────────────────┐
              │     PostgreSQL        │
              │  async_operations     │
              │  (status='pending')   │
              └───────────┬───────────┘
                          │ FOR UPDATE SKIP LOCKED
            ┌─────────────┼─────────────┐
            ▼             ▼             ▼
      ┌──────────┐ ┌──────────┐ ┌──────────┐
      │ Worker 1 │ │ Worker 2 │ │ Worker 3 │
      │(slots:10)│ │(slots:10)│ │(slots:10)│
      └──────────┘ └──────────┘ └──────────┘
```

### Ключевые файлы

| Файл | Назначение |
|------|-----------|
| `hindsight-api/hindsight_api/worker/main.py` | CLI и запуск worker'а |
| `hindsight-api/hindsight_api/worker/poller.py` | Polling-движок (ядро) |
| `hindsight-api/hindsight_api/engine/task_backend.py` | Абстракция: `BrokerTaskBackend` / `SyncTaskBackend` |
| `hindsight-api/hindsight_api/alembic/versions/l7g8h9i0j1k2_add_worker_columns.py` | Миграция БД |
| `scripts/dev/start-worker.sh` | Скрипт запуска |
| `hindsight-api/tests/test_worker.py` | Тесты |

### Типы задач

1. **`consolidation`** — Консолидация памяти / создание observations
2. **`batch_retain`** — Пакетное сохранение воспоминаний
3. **`refresh_mental_model`** — Обновление ментальной модели

### Конфигурация

```bash

HINDSIGHT_API_WORKER_ID=<hostname>             # ID для claiming
HINDSIGHT_API_WORKER_POLL_INTERVAL_MS=500      # Интервал опроса (мс)
HINDSIGHT_API_WORKER_MAX_RETRIES=3             # Макс. попыток
HINDSIGHT_API_WORKER_MAX_SLOTS=10              # Всего конкурентных задач
HINDSIGHT_API_WORKER_CONSOLIDATION_MAX_SLOTS=2 # Лимит на consolidation
HINDSIGHT_API_WORKER_HTTP_PORT=8889            # Health/metrics endpoint
```

### Ключевые механизмы

**1. Безопасное извлечение задач:**

```sql
SELECT * FROM async_operations
WHERE status = 'pending' AND task_payload IS NOT NULL
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT ...
```

**2. Slot-based rate limiting:**
- `max_slots=10` — общий лимит конкурентных задач
- `consolidation_max_slots=2` — отдельный лимит для тяжёлых консолидаций
- Retain-задачи выполняются даже когда consolidation-слоты заняты

**3. Дедупликация консолидации:**
- Только одна консолидация на банк одновременно
- Повторный запрос возвращает `deduplicated: true`

**4. Fire-and-Forget:**
- Worker создаёт asyncio task и не ждёт завершения
- Продолжает polling пока слоты свободны

**5. Восстановление после краша:**
- При старте: `recover_own_tasks()` сбрасывает «processing» задачи обратно в «pending»
- Предотвращает зависшие задачи

**6. Retry механизм:**
- Ошибка → `retry_count += 1`
- `retry_count >= max_retries` → `status = 'failed'`
- Иначе → `status = 'pending'` (обратно в очередь)

**7. Multi-tenant поддержка:**
- Динамическое обнаружение tenant/schema на каждом цикле опроса
- Не требует перезапуска при добавлении новых tenant'ов

### Три режима запуска

```bash

./scripts/dev/start-api.sh
# Worker стартует как часть FastAPI lifespan

# 2. Отдельный процесс
./scripts/dev/start-worker.sh
# или: hindsight-worker --worker-id=worker-1 --poll-interval=500

# 3. Docker (в start-all.sh)
# API + встроенный worker, или раздельные контейнеры
# HINDSIGHT_API_WORKER_ENABLED=false отключает встроенный worker
```

### Схема БД

Таблица `async_operations` (добавленные worker-колонки):

```sql

claimed_at TIMESTAMP        -- Когда задача захвачена

-- Индексы:
idx_async_operations_pending_claim ON (status, created_at)
    WHERE status='pending' AND task_payload IS NOT NULL
idx_async_operations_worker_id ON (worker_id)
    WHERE worker_id IS NOT NULL
```

## 6. Retention Modes — Режимы сохранения

### Обзор

Режимы сохранения контролируют агрессивность извлечения фактов из контента
при операции retain. Влияют на промпт-шаблон и схему ответа LLM.

### Три режима

| Режим | Философия | Результат |
|-------|-----------|-----------|
| **`concise`** (default) | Качество > количество | Меньше фактов, но каждый значим |
| **`verbose`** | Полнота > краткость | Максимум деталей по 5 измерениям |
| **`custom`** | Ваши правила | Зависит от пользовательских инструкций |

### Влияние на pipeline

```
Retain Pipeline:
                                                    ┌─── РЕЖИМ ВЛИЯЕТ
  Content → Chunking → [Fact Extraction] → Linking → Embedding → Storage
                              │
                    ┌─────────┴─────────┐
                    │ 1. Промпт-шаблон  │  ← concise/verbose/custom guidelines
                    │ 2. Схема ответа   │  ← ExtractedFact / ExtractedFactVerbose
                    └───────────────────┘

  Linking, Embedding, Storage — НЕ зависят от режима
```

### Ключевые файлы

| Файл | Назначение |
|------|-----------|
| `hindsight-api/hindsight_api/config.py:116-226, 308-317` | Конфигурация и валидация |
| `hindsight-api/hindsight_api/engine/retain/fact_extraction.py:435-850+` | Промпты и логика |
| `hindsight-api/hindsight_api/engine/retain/orchestrator.py` | Оркестратор |

### Concise — «Будет ли это полезно через 6 месяцев?»

```
SELECTIVITY - CRITICAL (Reduces 90% of unnecessary output)

ONLY extract facts that are:
✅ Personal info: names, relationships, roles, background
✅ Preferences: likes, dislikes, habits, interests
✅ Significant events: milestones, decisions, achievements, changes
✅ Plans/goals: future intentions, deadlines, commitments
✅ Expertise: skills, knowledge, certifications, experience
✅ Important context: projects, problems, constraints
✅ Sensory/emotional details: feelings, sensations, perceptions
✅ Observations: descriptions with specific details

DO NOT extract:
❌ Generic greetings: "how are you", "hello", pleasantries
❌ Pure filler: "thanks", "sounds good", "ok", "got it"
❌ Process chatter: "let me check", "one moment"
❌ Repeated info: if already stated, don't extract again

Format: 1-2 предложения на факт
Quality focus: QUALITY OVER QUANTITY
```

Промпт: `CONCISE_FACT_EXTRACTION_PROMPT` (строки 498-552)

### Verbose — «Захватить всё с максимумом деталей»

```
FACT FORMAT - ALL FIVE DIMENSIONS REQUIRED - MAXIMUM VERBOSITY

For EACH fact, CAPTURE ALL DETAILS - NEVER SUMMARIZE OR OMIT:
1. what:  COMPLETE description with ALL specifics (objects, actions, quantities)
2. when:  ALWAYS include temporal info with DAY OF WEEK
          Format: "day_name, month day, year" (e.g., "Saturday, June 9, 2024")
3. where: SPECIFIC locations, places, areas, regions
4. who:   ALL people/entities with FULL relationships and background
5. why:   ALL emotions, preferences, motivations, significance, nuance
```

Промпт: `VERBOSE_FACT_EXTRACTION_PROMPT` (строки 563-673)

### Custom — пользовательские правила

См. раздел [Custom Extraction Prompts](#4-custom-extraction-prompts--кастомные-промпты-извлечения).

Промпт: `CUSTOM_FACT_EXTRACTION_PROMPT` (строки 555-559)

## 7. External Hindsight API — Внешний API

### Обзор

> **Это общая фича, не только для OpenClaw!**

Возможность подключаться к удалённому Hindsight API серверу вместо запуска локального daemon.
Реализована на уровне `hindsight-embed` (Python), а OpenClaw — один из потребителей.

### Зачем это нужно

- **Shared memory** — несколько агентов работают с общей памятью
- **Production** — централизованный сервер, клиенты без ML-моделей
- **Команды** — общая база знаний для всех членов команды
- **Контейнеры/облако** — избежание тяжёлых зависимостей локально
- **Быстрый запуск** — не нужно загружать embedding/reranking модели

### Архитектура

```
Приложение (OpenClaw / CLI / SDK)
    │
    ▼

    │
    ├─ Задан → Использовать внешний API (daemon НЕ стартует)
    │           ├─ Health check на /health (с таймаутом 10 сек)
    │           └─ Все операции → HTTP к внешнему серверу
    │
    └─ Не задан → Запустить локальный daemon (традиционный flow)

```

## 8. Dynamic Per-Channel Memory Banks — Динамические банки по каналам

### Обзор

> **Это фича только для OpenClaw!** Но использует общий механизм банков из core API.

Автоматическая изоляция памяти по каналам связи (Slack, Telegram, Discord).
Каждый канал получает свой независимый банк памяти.

### Как работает

```
OpenClaw получает сообщение
    │
    ▼
deriveBankId(ctx, pluginConfig)
    │
    ├─ channelType = ctx.messageProvider  (slack / telegram / discord)
    ├─ channelId = ctx.channelId          (C12345 / 987654)
    ├─ prefix = pluginConfig.bankIdPrefix (опционально)
    │
    ▼
Bank ID: "{prefix?}-{channelType}-{channelId}"
    │
    Примеры:
    ├─ slack-C12345
    ├─ telegram-987654
    └─ prod-slack-C12345 (с prefix)
```

### Зачем это нужно

- **Изоляция контекста** — разговор в #general не влияет на #engineering
- **Автосоздание банков** — банк создаётся при первом использовании
- **Mission per bank** — каждый канал может иметь свою «миссию» агента
- **Предотвращение путаницы** — агент не смешивает контексты разных каналов

### Конфигурация

```json
// ~/.openclaw/openclaw.json
{
  "plugins": {
    "entries": {
      "hindsight-openclaw": {
        "config": {
          "dynamicBankId": true,        // По умолчанию включено
          "bankIdPrefix": "prod"         // Опционально
        }
      }
    }
  }
}
```

| Настройка | Результат |
|-----------|-----------|
| `dynamicBankId: true` (default) | Каждый канал → свой банк (`slack-C123`) |
| `dynamicBankId: false` | Все каналы → общий банк `openclaw` |
| `bankIdPrefix: "prod"` | Префикс к ID (`prod-slack-C123`) |

### Реализация

```typescript
// hindsight-integrations/openclaw/src/index.ts:82-101
function deriveBankId(ctx, pluginConfig): string {
  // Если динамические банки отключены — общий банк
  if (pluginConfig.dynamicBankId === false) {
    return pluginConfig.bankIdPrefix
      ? `${pluginConfig.bankIdPrefix}-openclaw`
      : 'openclaw';
  }

  const channelType = ctx?.messageProvider || 'unknown';
  const channelId = ctx?.channelId || 'default';
  const baseBankId = `${channelType}-${channelId}`;

  return pluginConfig.bankIdPrefix
    ? `${pluginConfig.bankIdPrefix}-${baseBankId}`
    : baseBankId;
}
```

### Lifecycle банков

1. **Первое сообщение в канале** → bank_id вычисляется → банк автосоздаётся
2. **Mission** задаётся один раз при создании (из `bankMission` config)
3. **Recall** перед ответом агента → запрос только к банку этого канала
4. **Retain** после ответа агента → сохранение в банк этого канала

### Ключевые файлы

| Файл | Назначение |
|------|-----------|
| `hindsight-integrations/openclaw/src/index.ts:82-101` | deriveBankId() |
| `hindsight-integrations/openclaw/openclaw.plugin.json:59-67` | Схема конфигурации |
| `hindsight-api/hindsight_api/engine/retain/bank_utils.py` | CRUD банков (core API) |

## 9. LiteLLM Gateway — Шлюз для LLM/Embeddings

## 10. PostgreSQL Schema Support — Поддержка нестандартных схем

### Обзор

Возможность использовать кастомные PostgreSQL схемы вместо дефолтной `public`.
Схема — это namespace в PostgreSQL, логически группирующий таблицы.
**Фундаментальная архитектура для multi-tenancy.**

### Зачем это нужно

1. **Multi-tenancy** — полная изоляция данных клиентов на уровне БД
2. **Shared database** — Hindsight в общей БД, где `public` занят
3. **Организационные стандарты** — именование схем по политике компании
4. **SaaS безопасность** — tenant A физически не может запросить данные tenant B

### Архитектура

```
PostgreSQL Database
    │
    ├─ public (default schema)
    │       └─ pgvector extension (глобально для всех схем)
    │
    ├─ tenant_acme (custom schema)
    │       ├─ banks
    │       ├─ memory_units
    │       ├─ documents
    │       ├─ entities
    │       └─ async_operations
    │
    └─ tenant_bigcorp (another custom schema)
            ├─ banks
            ├─ memory_units
            └─ ... (полный набор таблиц)
```

### Конфигурация

**Простое использование (одна кастомная схема):**

```bash
export HINDSIGHT_API_DATABASE_URL=postgresql://user:pass@host:5432/dbname
export HINDSIGHT_API_DATABASE_SCHEMA=hindsight
```

**Multi-tenant (через TenantExtension):**

Каждый запрос получает свою схему на основе JWT/API-key — см. раздел
«Multi-Tenant Flow» ниже.

### Multi-Tenant Flow

```
HTTP Request (с JWT/API-key)
    │
    ▼
TenantExtension.authenticate(request)
    │
    ├─ Validate JWT/API-key
    ├─ Extract tenant_id
    │
    ▼
return TenantContext(schema_name=f"tenant_{tenant_id}")
    │
    ▼
MemoryEngine использует эту схему для всех операций
    │
    ├─ retain → INSERT INTO tenant_acme.memory_units
    ├─ recall → SELECT FROM tenant_acme.memory_units
    └─ reflect → uses tenant_acme.* tables
```

### Пример: JWT-based TenantExtension

```python
# Из документации extensions.md
class JwtTenantExtension(TenantExtension):
    async def authenticate(self, context: RequestContext) -> TenantContext:
        token = context.get_header("Authorization").replace("Bearer ", "")
        payload = jwt.decode(token, self.jwt_secret, algorithms=["HS256"])
        tenant_id = payload.get("tenant_id")

        # Каждый tenant получает свою схему
        return TenantContext(schema_name=f"tenant_{tenant_id}")
```

### Миграции с поддержкой схем

```python
# migrations.py:98-159
def run_migrations(database_url, schema=None):
    """
    1. Создаёт схему если не существует
    2. Получает advisory lock per-schema (предотвращает race conditions)
    3. Запускает Alembic миграции в контексте схемы
    4. pgvector остаётся в public (доступен всем схемам)
    """
```

Каждый migration-файл использует helper для schema-aware SQL:

```python
# В migration-файле
def _get_schema_prefix():
    schema = context.config.get_main_option("target_schema")
    return f'"{schema}".' if schema else ""

def upgrade():
    schema = _get_schema_prefix()
    op.execute(f"CREATE INDEX ... ON {schema}table_name(...)")
```

### Advisory Locks

Для предотвращения гонок при параллельных миграциях используются PostgreSQL advisory locks:

```python
# migrations.py:34-43
def _get_schema_lock_id(schema: str | None) -> int:
    """Generate unique lock ID per schema for migration locking."""
    base = 0x48494E44  # 'HIND' in hex
    if schema:
        return base + hash(schema) % 0x10000
    return base
```
